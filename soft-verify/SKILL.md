# Soft-Verify — 软件工程 × AI 维护 双视角架构审计

对任意代码库执行六阶段审计，最终交付一份**经独立核验的优化清单**（BACKLOG）。
每条结论必须可追溯到证据（文件:行号 + 实测数字，或已核验的外部研究）；
未经核验的联网检索结论禁止入清单。全程不改业务代码。

**与 improve-codebase-architecture 的分工**：要「深模块重构机会卡片 + HTML 可视化
报告」用那个；要「全量审计 + 核验清单 + AI 协作专项」用本技能。两者可先后使用。

**总纪律**：证据而非断言。执行者的自评不可信（METR 2025 RCT：16 名资深开发者
自评快 20% 而实际慢 19%）——关键结论必须由独立子代理或可复现命令产出。

**Common Mistakes（历史上真实踩过的坑，勿重蹈）**：
- 用印象分（"耦合较高""不够清晰"）代替数字——每条结论必须 文件:行号 + 实测值
- 检索结论未核验直接入清单——二手误引普遍存在（如 "PR +154%/评审 +91%" 常被
  误挂 DORA 名下，实际出处是 Faros AI 遥测研究；引用任何数字前回一手来源）
- 审计完不反思就交差——取证准确 ≠ 审计完善，漏的通常是机制性根因而非现象
- 有备份就认为能恢复——没有恢复演练的备份不算恢复能力
- 把本技能写成一次性叙事文——它是可复用步骤书，产出才是叙事

## 阶段 0 · 准备（≤10 分钟）

1. 确定仓库根与审计范围（全仓 vs 指定模块）。
2. 建立工作目录 `<repo>/openspec/changes/soft-verify-<date>/` 存中间产物
   （仓库无 openspec 约定时用 `docs/audit-<date>/`）。
3. 基线采集（全部实测，写入 _baseline.md）。以下命令以 Python 项目为例，
   **按仓库主语言替换**（Go: `grep -rn "panic("` / `go test ./...` 统计；JS:
   jest mock 统计 / `fs.writeFileSync` 写点；Java: `FileWriter`——审计的是同类
   概念在该语言的存在）：
   - 文件/行数分布：`find . -name "*.py" -not -path "*/node_modules/*" | xargs wc -l | sort -rn | head -20`
   - 依赖锁定情况（requirements/package-lock/go.mod 等是否存在、是否锁版本）
   - 测试形态：单测/集成/e2e 各多少；mock 强度（Python: `grep -rc "monkeypatch\|mock" tests/`）
   - git 状态：未提交数、最近提交日期、.gitignore 是否覆盖运行产物
   - 数据存储形态（文件/DB）、最大单文件体积、写入口数量
   - 运行时产物体积（缓存/临时目录/备份）
4. 向用户确认未明的裁定（AskUserQuestion，已在指令中明确的跳过）：
   ①范围=只审计+固化清单（推荐）还是连带修复；
   ②清单条目按通用方法论陈述，还是绑定本项目上下文细写；
   ③产出清单路径。

**完成判据**：_baseline.md 有真实数字；裁定落档。

## 阶段 1 · 证据制全量审计（产出：audit.md）

按六个维度逐一取证。**每条结论 = 现象 + 文件:行号 + 实测数字 + 影响**，缺一即
降级为"待核实假设"并继续补证。

1. **架构与模块化**：最大文件/函数行数对照业界阈值（Google：函数 ~40 行；社区：
   文件 300–500 行）；渲染是否字符串拼 HTML/CSS/JS；派生逻辑是否每请求现算；
   双渲染栈/双入口并存；有没有"所有改动都必经同一文件"的冲突热点。
2. **数据层**：数据源清单（是否有两份并存、写入是否"成功但无效"——写 A 读 B）；
   写入口数量与原子性；schema 版本字段有无；数据生命周期（缓存/备份/僵尸目录的
   体积与保留策略）；多环境漂移对账能力。
3. **并发与生命周期**：模块级可变缓存数量与锁；读-改-写无锁点；长任务与请求
   生命周期是否耦合（重启丢任务史）；运行时池上限与回收。
4. **可靠性与可观测性**：logging 框架使用 vs print；静默 except 计数；健康检查
   端点；重试/降级是统一层还是散落补丁；流式端点的中止机制覆盖率。
5. **接口设计**：端点总数与死端点（前后端/脚本/测试交叉 grep 零引用者）；版本
   协商；错误体一致性；**安全假设**（认证/限速/暴露面——写进部署前提，非要求改）。
6. **工程流程**：提交粒度与积压；测试形态单一性；配置管理（代码 env 键全集 vs
   example 文件差集）；脚本写入是否有 dry-run+备份纪律。

**完成判据与失败回路**：抽 3 条结论交独立子代理复核文件:行号与数字。
- 全命中 → 通过。
- 有未命中 → 修正该条证据，扩大抽检至 5 条；连续两轮有未命中 → 该维度全部
  重取证。
- 核验子代理不可用 → 改用可复现命令自证（把命令与输出原样贴进审计正文），
  并在条目标注"自证未独立复核"。

## 阶段 2 · 多轮反思（闸门：不通过不进检索）

对阶段 1 产物做书面自问（写进 _reflection.md）。**轮次**：至少 2 轮，上限 3 轮；
每轮必须产出对上一轮的修正或补充，连续 2 轮零修正即收敛放行（收敛本身记入文档，
不得为过闸编造修正）。

每轮四个自问：
1. **数据准确性**：抽 5 条最惊人的数字重测——惊人结论错的代价最大。
2. **维度完备性**：对照阶段 3 开头列出的四类 AI 失败模式（事故/实证研究/官方
   文档/大文件与多会话），逐类问"这个失败模式在本仓库的对应现象查了吗"。
3. **根因三问**（每条问题都问）：机制性根因是否已堵（还是只治了现象）？是否存在
   双向分叉（两份数据/两套环境各自演化）？有无可恢复能力（备份 ≠ 能恢复，演练过吗）？
4. **评估 ≠ 完善**：列出"这轮可能还是漏了什么"。

**通过判据**：≥1 条真实自我修正或补充，且根因三问每条都有书面回答。
**不通过**（零修正且未收敛）→ 回阶段 1 换维度/换抽样重取证，再反思。

## 阶段 3 · AI 失败案例与实证研究联网检索（可降级）

派 1–2 个检索子代理（WebSearch/WebFetch），收集四类证据，**每条带 URL 并标注
一手/二手**。本节的样例锚点是**待核验种子**（该领域二手误引高发、检索曾出现
数字与归属错误）——只作检索起点，引用前必须经阶段 4 核验：

1. **著名事故**（近 3 年）：agent 删库/删生产环境、泄露、失控循环烧钱、幻觉资源、
   供应链投毒。锚点：Replit 删 SaaStr 库（2025-07）、AWS Kiro 删重建（2025-12）、
   Cursor/PocketOS 删库（2026-04）、Copilot #14108 整文件清空循环、Cline #8422
   覆写 .env。
2. **实证研究**（带数字带样本量）：METR 2025 RCT（16 人慢 19% 自评快 20%）、
   GitClear（1.5–2.1 亿行：重复块 8 倍、复制粘贴超重构）、DORA 2024（采纳+25%→
   稳定性 -7.2%）、Stack Overflow 2025（66% 抱怨 almost right）、Veracode（45% 带
   OWASP 漏洞）、幻觉依赖包 arXiv 2406.10279。⚠ 二手转引高发区：DORA 2025 的
   量化数字常被误挂（实际出处是 Faros AI 遥测研究），引用前逐条回官方报告。
3. **官方工具文档**（逐字引用，非搜索摘要）：agent 编辑工具的硬约束（Edit 精确
   字符串替换+唯一匹配；超长文件只回首页 PARTIAL）、指令文件长度指引（CLAUDE.md
   <200 行）、多会话 worktree 隔离、AGENTS.md 规范（closest-wins）、Google CL
   ≤100 行、context rot（性能随输入长度下降）。
4. **大文件/多会话失败模式**：定向编辑退化为整文件重写、多 agent 同文件互撞、
   context 超限截断。

**降级**：无网/检索失败时如实标注"未联网核验，仅本地经验"，阶段 4 换为"仅核验
本地数字"，清单条目打"未核验"标记。

**完成判据**：≥10 条事故/案例 + ≥5 项带数字研究，逐条有 URL 与证据等级。

## 阶段 4 · 增强核验（闸门：未核验不入清单）

**检索结论默认可疑**——二手转引与来源张冠李戴在 AI 编程话题上高发。派独立核验
子代理（不可用时执行者自核，但清单标注"未独立复核"）：

1. 分三路：事故真伪（访问原始 URL+HTTP 状态+引语比对）/ 研究数字（样本量+百分比
   对照一手）/ 官方文档（逐字引语，非摘要）。
2. 核验要求：判定三档（✅确认/⚠️部分→给出实际值/❌无法证实）；找不到一手来源的
   标注证据等级；**发现疑似编造必须点破**。
3. 修正写回检索产物：删除线保留原 claim + 修正值（证伪留痕，不静默移除）。
4. 阶段 1 的仓库数字若未经命令实测，此路一并补测。

**完成判据与失败回路**：核验报告存在；清单中每条外部证据标注核验状态。
- 有修正 → 正常（该领域首轮检索出错是常态）。
- 零修正 → 不直接放行：抽 2 条已"确认"项交叉复检（换检索词/换来源独立再查）；
  仍零出入则记录"经交叉复检"后放行。
- 核验子代理不可用 → 执行者按同一清单自核 + 全部条目降级标注。

## 阶段 5 · 优化清单固化（产出：BACKLOG）

写优化清单（约定路径 `<repo>/openspec/BACKLOG.md`，仓库无 openspec 约定时用
`docs/BACKLOG.md`，或用户指定路径）。**已存在清单时做增量合并**：已完成项核对
后勾选，新项插入对应优先级段，口径冲突以本次核验结论为准并注"更新于 <date>"。

结构：

```
✅ 已完成（勾选+日期+变更名）
P1 两周内（收益高成本低）/ P1 用户项（需用户在外部系统操作的，如密钥轮换）
P2 功能驱动再做
P3 结构性大件（明确触发条件/前置条件）
G · AI 协作专项（本阶段先留占位节，阶段 6 完成后回填定稿）
过程待办 / 被证伪留痕（删除线+原因）
```

每项必须三元组：**现状（带证据数字）/ 目标 / 验收标准（可执行命令或可观察行为）**。
头部写维护规则（完成勾选注日期；证伪划删除线）。同步更新项目状态文件指向清单。

**完成判据**：清单中零"无证据条目"；优先级排序有依据（解锁后续功能的程度）。
G 节回填后清单才算定稿。

## 阶段 6 · AI 协作专项（G 节，逐项对照检查）

用阶段 3 核验后的事故清单反查本仓库，产出专项待办。检查项与对应外部教训如下；
第三列由审计实查填充（**禁止套用其他项目的结论**）：

| 检查项 | 对应外部教训 | 本仓库实查（审计时填） |
|---|---|---|
| 仓库自带 AGENTS.md（<200 行，嵌套就近生效） | 纪律文件不在仓库内=clone 后 agent 失去全部约束 | （查：根目录/子目录有无） |
| 多会话并行编辑协议（worktree 隔离/文件所有权/单提交 ≤100–200 行） | 多 agent 同文件互撞无解，官方方案=worktree 强制隔离 | （查：git worktree、提交粒度、并行覆盖史） |
| 巨石文件拆分（先特征测试冻结→抽最独立块→绞杀） | Edit 唯一匹配在长重复文件中失效→整文件重写；context rot | （查：最大文件行数与被共改频度） |
| 验证文化（独立子代理复审/证据而非断言） | METR 自评偏差实证 | （查：流程中有无强制独立审查） |
| 依赖幻觉防护（审计工具/"不自动加依赖"纪律） | 幻觉包名稳定复现可被投毒 | （查：依赖锁定与扫描现状） |
| 上下文与记忆卫生（定期对账过期记忆/文档） | 长上下文性能衰减；记忆随代码演化腐坏 | （查：记忆/文档与代码事实的偏差） |
| 事故模式库（索引：事件-根因-防复发闸门） | 同款事故反复发生=教训未沉淀 | （查：历史事故散落何处） |

## 收尾

1. 清单定稿（G 节回填完成）+ 向用户报告：核心发现（≤5 条，每条一句）+ 建议
   实施顺序 + 与外部事故的同款对照。
2. 中间产物（baseline/audit/reflection/检索/核验）留在变更目录供后续修复变更
   引用；**不删**（证伪与修正历史是资产）。
3. 提醒用户：本技能只产出清单；修复请对每个 P1 项走变更流程（审计证据可直接复用）。
