# Longtime-Go — 长时间连续任务执行纪律

用户给出 hours 级任务（"干到早上6点"、"跑一下午"）时启用本技能。
目标：**每个小时都在产出**，而不是每小时只紧凑干 14 分钟就收工等唤醒。

两大设计基线（缺一即散架）：

1. **prompt 是临时的，工作区是持久的**——状态全部外化到磁盘，任何一次
   唤醒（= 全新上下文）都能从文件无损接续；跨轮记忆只靠交接文件，
   不靠会话历史（Anthropic harness 设计：context reset 是优势不是缺陷）。
2. **完成必须由证据支撑，不许自评了事**——没有可检验验收信号的任务
   不进循环（task-fit）；自评天然宽松，所以用**隔轮判定**模拟独立验证者。

## Phase 0 · 开局（第一个 tick，先对齐再干活）

1. `date` 拿当前时间，算出截止时刻与可用小时数。**结束时刻写进章程，
   是硬限制**（到点硬停，绝不超时开工新任务）。
2. 建立调度中枢文件（如 `memory/overnight-YYYY-MM-DD.md`），写入**任务章程**：
   - 核心目标（用户原话提炼，一句话）
   - 纪律红线（用户裁定的不可违项；含生产资产保护：如生产库 sha、
     服务只准经指定脚本重启）
   - 候选清单 ≥5 项（按价值排序）——这是防提前收工的弹药库
3. **任务准入三问**（night-flow task-fit，清单里每项过一遍，不过则改写或淘汰）：
   - **可检验**：能写出具体验收标准吗？（文件存在/测试通过/页面含某内容）
   - **可逆**：失败了能退回吗？破坏性、对外发送、花钱的任务不准入
   - **单轮可完成**：30–60 分钟能出可验收产出吗？太大的拆成多轮
   - **诊断类例外**：排查"为什么挂/为什么错"类任务写不出完成式验收标准
     （原因未知），验收标准改写为「产出定位结论文件 + 可复现路径」——
     检验结论产物本身，不许把"修好"当标准（那是修复类任务的事）
4. 每项任务**开工前写死验收标准**，记入中枢文件；做完不许追加修改
   （防"先做再补标准"的自评宽松）。
5. 与用户思维统一：章程贴给用户确认，**不阻塞等待**——声明默认即刻执行。
6. 挂定时唤醒（cron/调度器；间隔 ≈ 单任务最大时长，60 分钟任务配 60–70 分钟 tick）。
7. **立刻开始第一项**，不要等下一个 tick。

## Phase 1 · 每个 tick 的固定仪式（唤醒时按序执行）

1. **看时间**：已过结束时刻 → 跳 Phase 5 收尾；未到开始时刻 → 本轮不干活直接结束。
2. 读调度中枢文件 + `log.jsonl` → 找「准备做什么」。
3. **验收上轮（隔轮改判）**：读 log 里所有 `verdict=doing` 的行，
   **以文件/产物为准**逐条核对开工时写死的验收标准（不是回忆"我当时做了什么"）：
   - 证据齐全且达标 → 改判 `pass`，进入下一任务
   - 证据缺失或不达标 → 改判 `rework`，本轮优先回工
   - 同一任务连续 2 次 `rework` → 标 `blocked` 跳过，留给收尾 Briefing
   - **改判语义（append-only）**：log.jsonl 只追加不修改——改判 = 追加
     新行（引用被改判行的 `ts`/`task`，写新 verdict + 核对证据），原行不动。
     整点盒下每 tick 可完成多任务，**每任务独立一行、独立隔轮改判**。
4. 健康检查：服务/依赖探活；坏了先修（只准用指定重启脚本）。
5. **冒烟测试先于新代码**：跑一遍现有主链路，坏了先修损坏再叠新功能。
6. 从候选清单取**最高价值且本小时可完成**的一项。

## Phase 2 · 工作循环（★ 防止 14 分钟收工的核心规则）

**干完一项 ≠ 收工。** 时间盒 = 整点，不是任务数：

```
while (now < 整点前 10 分钟):
    取清单中下一项（或继续未完项）
    flow 立项 → 实现 → 验证 → 提交
    清单耗尽或全部阻塞时：
        深化已交付项（补测试/补文档/性能打磨）
        或自主提出新的有价值任务（从实测发现里长出来）写入清单
        ——不许输出"无事可做"
```

- 单项超一小时：拆半成品写入「准备做什么」，下个 tick 续做，不烂尾。
- 等待时间（浏览器回答/澄清超时/构建）**必须并行消化**：排队下一项的
  立项、写日志草稿、跑测试——不许干等。
- 被外部阻塞（上游挂起/依赖坏）：如实记录 + 降级做不受阻塞的项，
  **阻塞项标「未通过」不冒充完成**。

## Phase 3 · 验证闭环（每项修改必过）

- 真实操作验证：模拟用户真实操作（浏览器/CLI）看到真实表现 →
  截图/输出存档 → **读图/读输出判断效果**，不达标回炉。
- **读图不可用时的降级**（部分环境/模型收不了图片）：改用 DOM 快照、
  接口响应断言、日志断言等内容级验证，且记账时如实标注
  「视觉未过目」——降级不是冒充，缺口写进 Briefing。
- **evidence 必须是隔轮可查的文件路径**（截图/png、jsonl、测试输出、
  DOM 快照存档）——只存在于会话记忆里的证据对下一轮等于不存在。
- 全量测试绿 + 生产资产核对（如库 sha256）才允许提交。
- 提交信息写「为什么」和「验收证据路径」。
- 本轮只记 `doing`，**结论由下一 tick 依证据改判**（Phase 1 第 3 步）
  ——刚做完就自评 = 宽松偏差的温床。

## Phase 4 · 整点记账（每个 tick 收尾，强制）

**双轨记账**——markdown 给人读，jsonl 给下轮的"失忆自己"机器读：

1. 调度中枢文件追加四段式条目：
   - **做了什么**（证据 = 截图路径 + 提交号）
   - **发现了什么**（含推翻自己的纠正——假象要标注）
   - **诚实声明**（未通过/被阻塞的项，绝不冒充完成）
   - **准备做什么**（下一 tick 的第一行指令）
2. `log.jsonl` 追加一行（状态目录与中枢文件同放）：
   ```json
   {"ts":"2026-09-15T23:40:00","task":"任务名","evidence":"产出路径或可复查的具体内容","verdict":"doing","ac":"开工时写死的验收标准","next":"下轮计划一句话"}
   ```

## Phase 5 · 收尾（最后 tick / 收到停止 / 触发升级）

- 全量测试 + 全链路健康检查 + **Briefing 汇总**：pass/rework/blocked
  三类计数、关键产出路径、未解决问题、明日建议、未尽事项移交清单
  （附精确复现路径）。服务恢复到用户可用的干净态。
- 归档 log.jsonl → log-YYYYMMDD.jsonl，清空 plan 段。
- **连续升级熔断**：累计 3 个任务 blocked → 不硬撑，提前收尾出 Briefing。
  护栏：熔断是**唯一的合法提前收尾理由**——每条 blocked 必须附复现路径
  与已尝试手段（记在 log 里），防止熔断沦为偷懒的体面说法。

## 安全规则（commit gate，必须遵守）

- **不可逆动作留在循环体外**：改系统配置、删数据、对外发送、花钱操作
  ——一律不执行，log 标 `blocked` 写明「待主人决定」。
- **到点硬停**：结束时刻是硬限制，绝不超时开工新任务。
- **时段窗口自检**：每次唤醒先看时间，窗口外不干活。
- 生产资产红线随章程携带（如：生产库只读、sha256 逐 tick 核对、
  服务只准经指定脚本重启）。

## 经验铁律（实战换来，违反必踩）

- **改动生效重启链**：动手前盘点"改了 X 需要重启哪些进程"——
  常见暗病：应用服务重启了，但旁路工具/worker/插件进程还持有旧代码，
  表现为"改了没生效"的假象（浪费数小时的隐形坑）。
- **验证别信单源**：截图可能是陈旧帧、脚本直跑可能因环境差异假绿
  （渲染了 404 空页也算"通过"）。证据至少两个独立来源，或 instrument
  到失败现场再下结论。
- **唤醒仪式不可跳过**：每个 tick 都当自己失忆——先读文件再动手；
  验收上轮只认文件证据，不认记忆。
- **诚实 > 体面**：阻塞就说阻塞，验收不过就写未通过；夜间没人看着，
  冒充完成的代价是白天返工双倍。
- **emoji/多字节字符**：JS 里判断前缀用 `indexOf` 不用 `charAt(0)`；
  Python↔JS↔HTML 三层引号嵌套优先改用 JS 双引号字符串根治。
